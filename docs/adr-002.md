# ADR-002 — Simultaneous actions, ordered conflict resolution; full-observer step contract

**Status:** accepted

## Context

The environment step contract must support 2–4 agents acting per tick with a
deterministic, byte-identical replay guarantee. The only choices that matter are (a) how the multiple agent actions in one tick
interact, and (b) what the `Observation` exposes. The environment must never
read agent internals — only `AgentAction` values.

## Decision

1. **Simultaneous actions, two deterministic resolution passes.** Each tick
   takes one `AgentAction` per agent. The movement pass resolves all `Move`s
   (adversarial only on `ChokePoint` adjacency to the agent's pre-step zone;
   simultaneous — no occupancy blocking, agents may share a zone, unless the
   map's spatial capacity gates entry). The collection pass resolves all
   `Collect`s against the post-move zone, and a resource may be claimed by at
   most one agent per tick. Both passes resolve in ascending priority rank:
   `rank = (agentId + state.StepCount) % agentCount`. At zero-based tick `t`,
   the first agent is `(-t mod agentCount)` (nonnegative modulo), not
   `t mod agentCount`; the lowest-rank eligible contender wins. Agent polling
   remains in ascending agent id, and pathfinder neighbor ordering remains in
   ascending zone id.
2. **Invalid or missing actions degrade to `Wait`.** A move to a non-adjacent
   zone, a collect of a resource not in the agent's zone, or an agent id past
   the end of the action array are no-ops. A buggy agent can therefore never
   crash or wedge the simulation, and illegal-action handling is itself
   deterministic.
3. **Full observability.** `Observation` carries the whole `MapGraph`, every
   `AgentState` (zone + score), and the flat list of claimed resource ids;
   each agent gets its own `Observation` headed by its `AgentId`.
4. **Termination.** The tick is terminal when the step count reaches the
   `SimulationConfig.MaxTicks` limit or when every resource on the map has
   been claimed (a map with zero resources only ever ends by tick limit).
   Reward is +1 per resource collected. On terminal, the winner is the agent
   with the highest score; ties resolve to the lowest agent id.
5. **Initial placement.** Agent `i` round-robins to zone `i % zoneCount`, so
   starting layout is deterministic with no seed-side randomness in the
   environment (the seed's only job is map generation).
6. **Shared map model lives in `Lattice.Environment`.** `MapGraph`/`Zone`/
   etc. moved here so the step contract can expose the map while the
   Environment stays reference-free (BCL-only); the Generator depends on the
   Environment for both `Rng` and the map model. A reverse Environment →
   Generator edge would be a project-reference cycle and is impossible.

## Rationale

Simultaneous actions with a documented resolution order (moves then
collects; ascending tick-dependent priority rank) give deterministic progression
with no hidden state —
the same tick always rewrites to the same next state. Degrading invalid
actions to `Wait` keeps the simulation total (every `AgentAction` array yields a
valid next state), which is what makes whole-trajectory determinism testable
without a legal-action oracle in the environment. Full observability keeps the
rule-based agents trivially simple, per the "environment over agents"
principle.

## Consequences

- `AgentAction` is a single closed record (`Kind` + optional `ZoneId`/`ResourceId`)
  plus an `ActionKind` enum — data only, JSON round-trippable, no behavior.
- Conflict rules are explicit and unit-tested (same-resource contention,
  invalid moves, missing actions) before any agent exists.
- Environment step logic takes `(SimulationState, AgentAction[], SimulationConfig)`
  and returns a new immutable state; `LatticeEnvironment` and
  `SimulationDriver` are thin wrappers over that pure function.

## Addendum — Perception filtering is a projection, not a core change

The simulation still emits a full-observability `Observation` every tick, and
the terminal/winner/reward rules are untouched. The fog-of-war lives entirely
downstream, in `PerceptionFilter` — a pure function of a `SimulationState` and
an observer that produces a `PartialObservation` the agents actually consume:

1. **Vision is a hop-bound cone, not a core gate.** `SimulationConfig.Vision`
   bounds how many choke-edge hops an agent can see; the core is
   vision-agnostic and never masks anything — masking happens when an
   observer's perception is projected.
2. **Observed / Stale / Unknown.** `ZoneSight`, `ResourceSight`, and
   `AgentSight` carry a `KnowledgeStatus`: inside the cone this tick
   (`Observed`), seen before but out of cone (`Stale` — last-known data plus
   the sighting tick survive), or never seen (`Unknown` — masked). This is the
   "stale memory" the perception contract promises: geometry agents are entitled
   to is only what they have actually observed.
3. **Rule-based agents opt in.** `AgentBeliefMap` maintains known/stale/unknown
   territory and `ScoutCollectorAgent` plans over exits it has seen; agents
   that don't opt in keep seeing the full `Observation`.

**Consequences:** partial observability is testable without touching the
simulation core (masking is a pure projection, and `Tests/Environment/PerceptionFilterTests.cs`
asserts strictly masked data beyond V hops); trajectory recordings remain
full-fidelity because the recording format never lost information.

## Addendum — Multi-tick transit and spatial capacity

Movement is still resolved first, in ascending priority rank
`(agentId + state.StepCount) % agentCount`, as a total function.
Two new pieces join the move gateway:

1. **Opt-in kinematic traversal.** `SimulationConfig.TransitSpeed`
   defaults to `SimulationConfig.InstantTransit` (0), preserving the
   same-tick move for every existing caller and recording. A positive speed
   makes an adjacent-choke crossing take `max(1, ⌈ManhattanLength / speed⌉)`
   ticks — pure integer arithmetic. While crossing, the agent carries an
   `InTransit(From, To, RemainingTicks)` on its `AgentState`; `ZoneId` holds
   the departure node so perceptions and winner logic keep working, and an
   in-transit agent acts exactly like a (stationary) occupant of the departure
   node for capacity purposes. RemainingTicks is decremented once per tick and
   the agent arrives when it reaches zero — a 3-tick crossing arrives after
   exactly 3 ticks, and in-transit agents cannot move or collect. Transit
   state is plain serializable data, so JSONL trajectories faithfully capture
   mid-crossing frames and replay byte-identically.
2. **Capacity bounds.** `Zone.MaxOccupancy` and
   `ChokePoint.MaxOccupancy` (default `MapLimits.Unlimited`; 0 = impassable)
   constrain the move pass's entry gateway. Node capacity is a same-tick entry
   gate: capacity is computed from start-of-tick occupancy plus same-tick
   arrivals and transit bookings; a denied agent stays at its departure node.
   Choke capacity is only consulted for crossings that actually take more than
   one tick (instant moves don't occupy the edge) and persists for the whole
   tick an agent is mid-crossing, so it is the durable guardrail against a
   queue of simultaneous crossings. Both gates are triaged in ascending
   priority rank `(agentId + state.StepCount) % agentCount` — the
   lowest-rank eligible contender wins, deterministically, every time.
3. **Choke priority-yield.** Because move and capacity resolution run in
   ascending priority rank, two opposing crossings of a capacity-1 choke can
   never
   livelock: the lower-rank agent resolves first and reserves the edge, and the
   yielding agent is denied entry and stays put, re-attempting on a later
   tick — the high-traffic chokepoint degenerates to a deterministic turnstile
   rather than a deadlock.

Deliberate simplifications: node capacity is *not* a reservation across
ticks (a multi-tick crossing that books a capped node is not un-booking the
same slot through the whole crossing — the edge gate carries that burden), and
`ActionSpace` remains a syntactic-only checker: a move into a saturated zone is
well-formed and gets rejected at runtime, which is what the trajectory records.

**Consequences:**
- `AgentState` gained an optional `InTransit? Transit`; old recordings without
  the field deserialize to `null` (fully compatible with the pre-kinematic format).
- `TransitTicks(map, from, to, speed)` is a public pure function so tests and
  tooling compute expected crossing durations with the exact same arithmetic.
- Capacity rejection and transit progression are both observable in `StepResult`
  observations and covered by dedicated unit tests + trajectory replay tests.

## Addendum — Forking is free because state is immutable

Counterfactual analysis builds on the immutability the step
contract already guarantees: `SimulationState` is an immutable record, so a
"snapshot" is a shared reference — nothing to deep-copy, nothing to tear.

- `SimulationFork` wraps a captured `SimulationState` plus the same
  `SimulationConfig`; stepping it calls the pure `Simulation.Step`, so a forked
  replay is byte-identical for identical action sequences and can never mutate
  the source state, its owning trajectory, or any sibling fork (provably — the
  shared records are immutable).
- `CounterfactualEvaluator` re-rolls a recorded trajectory from branch tick K
  with an alternative action sequence and reports score deltas, winner delta,
  and steps-to-completion divergence — the "what-if" layer the MCTS agent
  rolls out per candidate action.

## Addendum — The fairness arena mirrors positions, not rules

Structural spawn bias is measured with mirrored head-to-head
episodes. Because initial placement binds spawn to agent id (`CreateInitial`
round-robins agent i to zone i), "seat the same contestants at swapped spawns"
cannot be spelled by swapping agent ids — the environment would put agent 0 on
spawn A regardless. The mirror is spelled on the map instead: the two spawn
territories (zones 0 and 1, their resident resources, and every incident choke
endpoint) are exchanged, and the same two-slot roster replays the swapped map.
The bias index is then territory-attributed across both seats — see
`docs/adr-003.md`.
